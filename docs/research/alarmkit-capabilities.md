# AlarmKit capabilities and constraints for Snoozeloo (iOS 26)

Resolves [#2](https://github.com/IgorJonski/Snoozeloo/issues/2). Researched 2026-09-05 against primary sources only: Apple's AlarmKit reference, the WWDC25 session "Wake up to the AlarmKit API", Apple's sample "Scheduling an alarm with AlarmKit", Apple Developer Forums replies by Apple engineers (DTS), Apple release notes, and Kotlin/Native interop docs. Where a claim could not be confirmed from such a source, this note says so.

## Summary

AlarmKit (iOS 26.0+) covers Snoozeloo's core: one-shot and weekday-repeating alarms, a 5-minute snooze (`postAlert: 300`), a bundled custom sound, a lock-screen alert with a custom title (the "WORK" label), and App Intents that run in the app process when Turn Off / Snooze are tapped. It does **not** allow per-alarm volume or vibration control, offers no way to show the app's own Trigger screen *instead of* the system alert, and custom sounds inherit the notification-sound rules (aiff/wav/caf in PCM/IMA4/µ-law/a-law, under 30 s). The framework is Swift-only, so Kotlin/Native reaches it through a Swift class that implements a Kotlin interface. Test on a physical device: Apple DTS says the simulator "does not function properly with AlarmKit" and asks developers to use hardware. ADR-0001 can move to **accepted** with the degradations listed at the end.

## Details

### 1. Custom alarm sounds

- **API.** `AlarmManager.AlarmConfiguration(countdownDuration:schedule:attributes:stopIntent:secondaryIntent:sound:)` takes `sound: AlertConfiguration.AlertSound` (an ActivityKit type). Cases: `.default` and `.named(String)`. Apple: "You can also include custom sounds for your alarm." — [AlarmConfiguration](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmconfiguration), [AlertSound](https://developer.apple.com/documentation/activitykit/alertconfiguration/alertsound). (The overview code on that page shows an `alertConfiguration:` parameter that does not exist in any documented initializer; use `sound:`.)
- **Location.** `named(_:)`: "Choose a file that's in your app's main bundle or the `Library/Sounds` folder of your app's data container." — [AlertSound.named](https://developer.apple.com/documentation/activitykit/alertconfiguration/alertsound/named(_:)). WWDC25: "You will need to specify the name of the sound file, which should be either in your app's main bundle or Library/Sounds folder of your app's data container." — [WWDC25-230](https://developer.apple.com/videos/play/wwdc2025/230/).
- **Format and length.** Neither the AlarmKit nor the ActivityKit page states a format or a length limit. The closest primary statement is DTS (Kevin Elliott, April 2026): AlarmKit "playback goes through the same infrastructure as the notification system" — [thread 821315](https://developer.apple.com/forums/thread/821315). The notification-sound rules are: Linear PCM, MA4 (IMA/ADPCM), µ-Law, a-Law packaged as `aiff`, `wav`, or `caf`; "Sound files must be less than 30 seconds in length. If the sound file is longer than 30 seconds, the system plays the default sound instead." — [UNNotificationSound](https://developer.apple.com/documentation/usernotifications/unnotificationsound). Treat the < 30 s / caf rule as the safe authoring constraint; developer reports on the forums are consistent with it (mp3 under 30 s worked on 26.1 in [thread 807752](https://developer.apple.com/forums/thread/807752); "I recommend sounds shorter than 30 seconds" in [thread 788836](https://developer.apple.com/forums/thread/788836)), but Apple has not confirmed it for AlarmKit specifically. **Unconfirmed:** whether a custom sound loops for the whole alerting period the way `.default` does — one developer reported looping working on 26.1 ([thread 807752](https://developer.apple.com/forums/thread/807752)); no Apple statement.
- **Known bug.** On iOS 26.0 custom sounds played a system error tone; Apple engineer: "There is a known issue which is being fixed in iOS 26.1." — [thread 802620](https://developer.apple.com/forums/thread/802620).
- **Built-in Clock tones.** DTS: "there is no public API that allows developers to access or directly play the built-in iOS alarm sounds ... you are currently limited to using custom audio files" — [thread 808251](https://developer.apple.com/forums/thread/808251). This matches the map's decision that iOS lists sounds bundled with the app.
- **Silent mode / Focus.** "It overrides both a device's focus and silent mode, if necessary." — [sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit). FAQ: "AlarmKit alarms can break through all focus modes." — [thread 797158](https://developer.apple.com/forums/thread/797158).

### 2. Volume and vibration

- **Volume.** DTS (Albert Pascual, Jan 2026): "AlarmKit does not directly support volume customization beyond utilizing the system ringer volume. ... there is no API in AlarmKit that allows for volume modification" — [thread 813519](https://developer.apple.com/forums/thread/813519). DTS (April 2026): alert volume is tied to Settings › Sounds & Haptics › "Ringtone and Alerts"; no supported API to read or change it — [thread 821315](https://developer.apple.com/forums/thread/821315).
- **Vibration.** No parameter for haptics exists on `AlarmConfiguration`, `AlarmAttributes`, `AlarmPresentation`, or `AlertSound` ([AlarmConfiguration](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmconfiguration), [AlarmAttributes](https://developer.apple.com/documentation/alarmkit/alarmattributes)). The map's "Silent keeps the Trigger screen and vibration" cannot be implemented as a *vibrate-only* AlarmKit alarm: Silent on iOS means `.default` sound (or a near-silent bundled file) with the system's haptics. **Unconfirmed:** whether haptics play at all when the device is unlocked — one unanswered forum report says only a short vibration occurs with the screen on ([thread 808260](https://developer.apple.com/forums/thread/808260)).

### 3. Schedules: weekday-repeating and one-shot

- `Alarm.Schedule` has two cases: `fixed(Date)` — "A one-shot alarm that fires at a specific time, not a time relative to the current time zone." — and `relative(Alarm.Schedule.Relative)` — "An alarm that can repeat and fire at a time relative to the device's current time zone." — [Alarm.Schedule](https://developer.apple.com/documentation/alarmkit/alarm/schedule-swift.enum).
- `Relative(time: Time(hour:minute:), repeats:)` where `repeats` is `.never` (one-shot) or `.weekly([Locale.Weekday])`; WWDC25 example `.weekly([.monday, .wednesday, .friday])` — [WWDC25-230](https://developer.apple.com/videos/play/wwdc2025/230/), [sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit).
- Persistence: "all alarms are expected to persist regardless of app or device state changes, once they are successfully scheduled." Limit: no fixed number; `maximumLimitReached` error when the device refuses — [thread 797158](https://developer.apple.com/forums/thread/797158).
- Snoozeloo mapping: One-shot → `.relative(time, repeats: .never)` (keeps "07:00 local" semantics across time-zone changes — matches the map's rule that a passed One-shot schedules tomorrow); weekday alarm → `.weekly(days)`. `.fixed` is only for absolute instants and would drift on travel.
- Observe state with `AlarmManager.shared.alarmUpdates`; "An `Alarm` that's not included in the `AlarmManager.alarmUpdates` asynchronous stream is no longer scheduled with AlarmKit." — [sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit). Note: after a one-shot fires and is stopped it drops out of this stream; Snoozeloo must flip the Alarm to Disabled itself (from the stop intent or on next launch).

### 4. Five-minute snooze

- `Alarm.CountdownDuration(preAlert:postAlert:)`: `postAlert` is "The duration applied after the alarm has alerted at least once and moves back to the countdown state." — [CountdownDuration](https://developer.apple.com/documentation/alarmkit/alarm/countdownduration-swift.struct). Apple's `Alarm` reference example: `CountdownDuration(preAlert: nil, postAlert: 9 * 60)` described as "an alarm that includes a 9 minute snooze option" — [Alarm](https://developer.apple.com/documentation/alarmkit/alarm). Snoozeloo uses `postAlert: 5 * 60`.
- The secondary button snoozes when `secondaryButtonBehavior: .countdown`: it "re-triggers the alarm after a certain `TimeInterval`, as specified in `Alarm.CountdownDuration.postAlert`" — [sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit). WWDC25: "If the alarm is snoozed the countdown UI will appear again for the duration of the post-alert interval. Once this interval elapses, the alarm will fire again and can be snoozed or dismissed." — [WWDC25-230](https://developer.apple.com/videos/play/wwdc2025/230/).
- The snooze countdown can also be started programmatically: `AlarmManager.countdown(id:)` "Performs a countdown for the alarm with the specified ID if it's currently alerting." — [AlarmManager](https://developer.apple.com/documentation/alarmkit/alarmmanager).
- **Widget extension is mandatory** for any alarm with a countdown: "AlarmKit expects a widget extension if an app supports a countdown presentation. Otherwise, the system may unexpectedly dismiss alarms and fail to alert." — [sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit). WWDC25: "If your alarm supports countdown functionality, your app is required to implement it using a Live Activity." — [WWDC25-230](https://developer.apple.com/videos/play/wwdc2025/230/). Consequence: the `iosApp` needs a small SwiftUI widget-extension target for the snooze countdown (Lock Screen / Dynamic Island). This is system UI, not a hand-built screen, but it is SwiftUI code outside Compose.
- Snooze cannot be fully disabled: hardware buttons can still snooze/stop; Apple engineer asked for a bug report rather than confirming a way to disable it — [thread 787509](https://developer.apple.com/forums/thread/787509), [thread 787490](https://developer.apple.com/forums/thread/787490). FAQ: "Any physical button that causes a reaction from AlarmKit will stop the currently alerting alarm." — [thread 797158](https://developer.apple.com/forums/thread/797158).

### 5. How Turn Off / Snooze reach the app

- `AlarmConfiguration` accepts `stopIntent: (any LiveActivityIntent)?` and `secondaryIntent: (any LiveActivityIntent)?` — [AlarmConfiguration](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmconfiguration). Sample: "When a person taps the button in the alerting UI, the `AlarmManager` automatically handles stop or countdown functionalities, depending on the button type. Tip: You can add additional actions for each button type using App Intents" — [sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit).
- `LiveActivityIntent`: "When the system performs the intent, the system launches your app process without opening the app, performs the intent" — [LiveActivityIntent](https://developer.apple.com/documentation/appintents/liveactivityintent). So `perform()` runs inside the Snoozeloo process in the background, where the Kotlin framework can be called (e.g. to mark a One-shot Disabled or log the Occurrence).
- FAQ: "When an alarm is dismissed, the `stopIntent` set in the `AlarmConfiguration` is called. Any code in the perform method of this `AppIntent` would execute." — [thread 797158](https://developer.apple.com/forums/thread/797158).
- `secondaryIntent` caveat: "This is only available after first unlock." — [AlarmConfiguration](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmconfiguration).
- Opening the app: set `static var openAppWhenRun = true` on the intent; WWDC25: "It also sets the openAppWhenRun flag to true to indicate that I want my app to be opened when the intent is executed. Once my app is opened, I can do additional tasks like show a more detailed view for the alarm with that identifier." — [WWDC25-230](https://developer.apple.com/videos/play/wwdc2025/230/).
- Note: with `.countdown` behaviour the system performs the snooze itself; the intent should not call `stop`/`countdown` again (a forum observation reports `AlarmManager.shared.stop(id:)` inside the stop intent errors because the system already stopped it — developer report only, no Apple statement).

### 6. What the alert can show; full-screen Compose Trigger

- Content: `AlarmPresentation.Alert(title:secondaryButton:secondaryButtonBehavior:)`; "The system provides a stop button automatically." Title is a `LocalizedStringResource` — [AlarmPresentation.Alert](https://developer.apple.com/documentation/alarmkit/alarmpresentation/alert-swift.struct). Buttons: `AlarmButton(text:textColor:systemImageName:)` — [AlarmButton](https://developer.apple.com/documentation/alarmkit/alarmbutton). `tintColor` colours the secondary button and title — [AlarmAttributes](https://developer.apple.com/documentation/alarmkit/alarmattributes), [WWDC25-230](https://developer.apple.com/videos/play/wwdc2025/230/). WWDC25: "In the alert, people are presented with the custom alarm title, as well as the name of your app." Since iOS 26.1 the custom `stopButton` is deprecated ("stopButton is deprecated and will no longer be used") — [deprecated init](https://developer.apple.com/documentation/alarmkit/alarmpresentation/alert-swift.struct/init(title:stopbutton:secondarybutton:secondarybuttonbehavior:)). So "WORK" goes into `title`; the alert cannot show Snoozeloo's own layout, the alarm time, or a body text.
- Paired watch: "The system forwards the alert presentation to a paired watch (if any)" — [sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit).
- Unlocked device: no Apple page describes the unlocked presentation. WWDC25 only says the alert "breaks through the silent mode and the current focus" and that countdowns show "on the Lock Screen as well as in the dynamic island and in StandBy". Developer reports describe a banner / Dynamic Island rather than a full-screen alert when unlocked ([thread 808260](https://developer.apple.com/forums/thread/808260), [thread 788836](https://developer.apple.com/forums/thread/788836)) — treat as unconfirmed.
- App's own Trigger screen: there is no API to replace the system alert with app UI or to auto-launch the app when the alarm fires. The only route is a user tap: a `.custom` secondary button + `openAppWhenRun = true` opens the app ([WWDC25-230](https://developer.apple.com/videos/play/wwdc2025/230/), [sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit)). But the secondary button is a single slot: it is either Snooze (`.countdown`) or Open (`.custom`), not both. For Snoozeloo the system alert (Turn Off + Snooze) is the Trigger on iOS; the Compose Trigger screen is reachable only if the app happens to be foregrounded (via `alarmUpdates` reporting `.alerting`) — **verdict: partial**.

### 7. Authorization and Info.plist

- Key: `NSAlarmKitUsageDescription` (String), iOS 26.0+: "If the `NSAlarmKitUsageDescription` key is missing or its value is an empty string, your app can't schedule alarms with AlarmKit." — [NSAlarmKitUsageDescription](https://developer.apple.com/documentation/bundleresources/information-property-list/nsalarmkitusagedescription).
- Flow: `AlarmManager.shared.requestAuthorization()` → `.notDetermined | .authorized | .denied`; "If a person using your app denies authorization, all attempts to schedule alarms fail." — [requestAuthorization](https://developer.apple.com/documentation/alarmkit/alarmmanager/requestauthorization()). Auto-prompt: "when a person adds their first alarm, AlarmKit automatically requests this authorization on behalf of the app" — [sample](https://developer.apple.com/documentation/alarmkit/scheduling-an-alarm-with-alarmkit). Users can change it later in Settings; observe with `authorizationUpdates` — [AlarmManager](https://developer.apple.com/documentation/alarmkit/alarmmanager), [WWDC25-230](https://developer.apple.com/videos/play/wwdc2025/230/).
- Other plist/entitlements: the widget extension needs the usual Live Activity setup (`NSSupportsLiveActivities`, per ActivityKit). There is **no** AlarmKit entitlement; `com.apple.developer.alarmkit` is fabricated and breaks device builds — Apple engineer in [thread 797950](https://developer.apple.com/forums/thread/797950).
- Constraint: "Hidden or passcode required apps do not work with AlarmKit. Currently, any scheduled alarms by such apps will silently fail." — [thread 797158](https://developer.apple.com/forums/thread/797158).

### 8. Simulator

- Scheduling and the authorization prompt work in the simulator ([thread 797950](https://developer.apple.com/forums/thread/797950)). Since the iOS 26.1 simulator, alerts do not fire while the simulated screen is locked; DTS (Nov 2025): "the new beta simulator version does not function properly with AlarmKit. Consequently, we consistently request that users utilize a physical device to test the functionality." — [thread 806998](https://developer.apple.com/forums/thread/806998). No Xcode 26.x release note mentions AlarmKit ([Xcode 26.1](https://developer.apple.com/documentation/xcode-release-notes/xcode-26_1-release-notes), [Xcode 26.2](https://developer.apple.com/documentation/xcode-release-notes/xcode-26_2-release-notes)). Implication for the map's open question: iOS alarm behaviour cannot be verified in CI on simulators; keep CI to Android/JVM plus iOS unit tests.

### 9. Swift-only; bridge pattern for KMP

- AlarmKit symbols are documented with `interfaceLanguage: swift` only and no Objective-C variant; the API uses Swift structs, enums with payloads, generics (`AlarmAttributes<Metadata>`), `async throws`, and `AsyncSequence` — [AlarmManager](https://developer.apple.com/documentation/alarmkit/alarmmanager), [Alarm](https://developer.apple.com/documentation/alarmkit/alarm). None of that is representable in an Objective-C header.
- Kotlin/Native: "Kotlin/Native provides indirect interoperability with Swift through Objective-C." and "A Swift library can be used in Kotlin code if its API is exported to Objective-C with `@objc`. Pure Swift modules are not yet supported." — [native-objc-interop](https://kotlinlang.org/docs/native-objc-interop.html). Swift export is Alpha and one-directional (Kotlin → Swift) — [native-swift-export](https://kotlinlang.org/docs/native-swift-export.html). So Kotlin cannot call AlarmKit directly.
- Recommended bridge (consistent with ADR-0003 "Swift only as a bridge"): declare a Kotlin interface in `shared` (e.g. `AlarmScheduler` with `schedule(alarm)`, `cancel(id)`, `authorizationState()`, and a callback/flow for updates); a Kotlin `interface` maps to a Swift `protocol` ([native-objc-interop mappings](https://kotlinlang.org/docs/native-objc-interop.html)), so `iosApp` implements it in a Swift class (`AlarmKitScheduler`) that owns `AlarmManager.shared`, the `LiveActivityIntent`s, and the widget extension's `AlarmAttributes<SnoozelooMetadata>`; pass the instance into Koin at `initApp(...)` from `iOSApp.swift`. Keep the Swift surface thin: data in/out as plain Kotlin classes (ids as `String`, times as hour/minute ints, weekdays as ints), no AlarmKit types across the boundary. The `perform()` bodies of the intents call back into the shared framework (same process) to update the Alarm/Occurrence state.

### 10. iOS 26.1+ changes

- **26.1**: `AlarmPresentation.Alert.init(title:stopButton:...)` and `stopButton` deprecated ("stopButton is deprecated and will no longer be used"); use `init(title:secondaryButton:secondaryButtonBehavior:)` — [deprecated init](https://developer.apple.com/documentation/alarmkit/alarmpresentation/alert-swift.struct/init(title:stopbutton:secondarybutton:secondarybuttonbehavior:)). Custom-sound error-tone bug fixed ([thread 802620](https://developer.apple.com/forums/thread/802620)); developer report of "Slide to stop" replacing tap-to-stop ([thread 807752](https://developer.apple.com/forums/thread/807752)). Simulator lock-screen alert regression ([thread 806998](https://developer.apple.com/forums/thread/806998)).
- **26.2 – 26.4**: no AlarmKit entry in the iOS release notes ([26.1](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-26_1-release-notes), [26.2](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-26_2-release-notes), [26.3](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-26_3-release-notes), [26.4](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-26_4-release-notes)). A 26.2 beta 3 regression where 26.1-scheduled alarms stopped ringing was reported fixed by the 26.2 RC (developer report, FB21273655) — [thread 809398](https://developer.apple.com/forums/thread/809398).
- **27.0 (beta as of 2026-09-05)**: new `AlarmConfiguration` initializer/factory variants adding `appEntityIdentifier:` ("The entity associated with the alarm") — [27.0 init](https://developer.apple.com/documentation/alarmkit/alarmmanager/alarmconfiguration/init(countdownduration:schedule:attributes:appentityidentifier:stopintent:secondaryintent:sound:)). No WWDC26 session is dedicated to AlarmKit ([WWDC26 videos](https://developer.apple.com/videos/wwdc2026/)). Minimum stays 26.0; target the non-deprecated 26.1 initializers.

## Recommendation for ADR-0001

**Move ADR-0001 from proposed to accepted**: AlarmKit on iOS 26.0+ delivers the alarm contract Snoozeloo needs — reliable wake-up alerts that break Silent/Focus, weekday repeats, one-shots, a 5-minute snooze, a bundled sound, and app-side hooks on Turn Off/Snooze — and no other iOS mechanism does (local notifications cap sound at 30 s and cannot loop or break Focus; DTS points alarm apps to AlarmKit in [thread 833511](https://developer.apple.com/forums/thread/833511)). Record these degradations in the ADR and in the specs:

1. **Volume**: the per-alarm volume slider has no effect on iOS alerts; hide it or relabel it as controlling only in-app preview playback. Alarms play at the system "Ringtone and Alerts" level.
2. **Vibration**: no per-alarm toggle on iOS; the system decides haptics. "Silent" on iOS = default sound plus system haptics (or a near-silent bundled file), not vibrate-only.
3. **Ringtone**: iOS lists bundled files only (as already decided); author them as `caf` (IMA4 or PCM) under 30 s. Whether a custom file loops for the whole alert like `.default` is unconfirmed — verify on 26.1+ hardware before committing to custom sounds; otherwise ship `.default` as the fallback.
4. **Trigger screen**: on iOS the system alert *is* the Trigger (title "WORK", Turn Off, Snooze). The Compose Trigger appears only if the app is in the foreground when the alarm fires. Decide in the "iOS Trigger experience" fog item that the secondary button is Snooze (`.countdown`), not Open.
5. **Extra native code**: a SwiftUI widget-extension target for the snooze countdown Live Activity is mandatory (system requirement), plus the Swift bridge class and two `LiveActivityIntent`s. This is within ADR-0003's "Swift only as a bridge" spirit but should be named explicitly.
6. **Testing**: iOS alarm alerting must be verified on a physical device; simulators cannot be trusted for the alert phase.
7. **Authorization UX** (fog item): handle `.denied` by showing a clear in-app state and a deep link to Settings; alarms silently fail if the app is hidden or passcode-locked.
